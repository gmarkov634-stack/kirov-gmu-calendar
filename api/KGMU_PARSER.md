# КГМУ: серверный парсер и очередь ручной проверки

## Назначение

Слой внедряет автоматический разбор XLSX Кировского ГМУ в тот же API, который обслуживает семестровые и годовые подписки.

Главный принцип: **новый XLSX не заменяет опубликованное расписание, пока парсер и QA не подтвердили результат и не выполнен publish-переход**. Неизвестная структура, неоднозначность, несовпадение учебного периода или ошибка QA создают `REVIEW_REQUIRED`; текущие календари покупателей остаются прежними.

## Поток данных

```text
официальные страницы расписания КГМУ
  -> watcher: фильтр учебного года/семестра + SHA-256
  -> новый/изменённый XLSX
  -> structural XLSX reader (cells + native merged ranges)
  -> classifier R / C / S / UNKNOWN
  -> parser R / C / S
  -> normalized staging
  -> QA
  -> PASS -> READY_TO_PUBLISH -> Telegram владельцу
       -> manual publish (default)
       -> automatic publish only when KGMU_AUTO_PUBLISH=true
  -> UNKNOWN / QA FAIL / parser error / period mismatch
       -> REVIEW_REQUIRED -> Telegram владельцу
```

## Статус типов

- `R` — недельная сетка по дням недели и группам: **включён через staging/QA/publish gate**.
- `C` — цикловая сетка старших курсов: **включён через staging/QA/publish gate**.
- `S` — смешанная недельно-цикловая структура: **включён через staging/QA/publish gate**.
- `UNKNOWN` — неизвестная сигнатура; публикация запрещена, создаётся `REVIEW_REQUIRED`.

Классификатор проверен на реальных исходных КГМУ:

```text
1_lech._1potok-16-03-2026-13.xlsx              -> R
4_kurs_lechebnyy_fakultet-02-02-2026-14.xlsx -> C
2_stomat-07-05-2026-15.xlsx                   -> S
```

## Верификация R

Парсер `R` сверялся с вручную проверенным расписанием лечебного факультета, группы 101–110, второй семестр 2025/26.

Контрольный результат:

- 119/119 исходных учебных anchor-блоков покрыты;
- 2654 события;
- по группам: `101=265, 102=265, 103=266, 104=266, 105=266, 106=265, 107=264, 108=265, 109=266, 110=266`;
- 0 необработанных блоков;
- 0 необъяснённых временных пересечений после правил замещения;
- проверки дополнительных занятий из примечаний проходят;
- полное сравнение с эталонным календарём дало 0 отсутствующих и 0 лишних событий по группе, названию, дате, времени, месту и форме аттестации.

Парсер сохраняет происхождение события (`sourceCell`, `sourceRange`, SHA-256 XLSX), поэтому QA может связывать нормализованное событие с исходной ячейкой.

## Верификация C

Цикловый парсер реализует C01–C13: календарную сетку конкретных дат, native merged ranges циклов, `*`, `М`, потоковые лекции факультетской терапии, физкультуру, справочную таблицу времени/баз и разрешённые C13-конфликты.

Автоматический regression workflow скачивает официальный исходный XLSX и проверяет не только счётчики, но и SHA-256 канонического набора событий.

Эталон:

- 2230 событий;
- 220/220 основных блоков;
- 0 дублей;
- 2 разрешённых C13-пересечения;
- точные групповые счётчики 401–420;
- canonical digest `f2afeeff15c12502993f517dd6ef2b6b6f2c458b6c4d824e0fc1b92c56064a62`.

## Верификация S

Смешанный парсер реализует S01–S07: недельную сетку, встроенный ежедневный цикл «Пропедевтическая стоматология», четверговое специальное время, нормализацию дисциплин, исправление `2603 -> 26.03`, сохранение source-source конфликтов и поиск первых двух реально свободных часов куратора.

Год конкретных `dd.mm` определяется из учебного года/семестра и фактического семестрового диапазона в заголовке исходного XLSX; это предотвращает ошибочную привязку весенних дат к первому году учебного года.

Автоматический regression workflow скачивает официальный исходный XLSX стоматологии 291–294 и проверяет:

- 830 событий;
- 62/62 исходных блока;
- 0 дублей;
- 13 разрешённых S04-пересечений;
- группы: `291=208, 292=208, 293=207, 294=207`;
- canonical digest `2144bbbef763a295688fd6781ffdd1908d33074fd9c9ba76216e0104eaebc44b`.

## Мониторинг официального сайта

Watcher читает три официальные страницы:

```text
Лечебный факультет      https://kirovgma.ru/lechebnyy-fakultet-raspisanie
Педиатрический факультет https://kirovgma.ru/raspisanie-pediatricheskiy-fakultet
Стоматологический факультет https://kirovgma.ru/raspisanie-stomatologicheskiy-fakultet
```

Из текста XLSX-ссылки извлекаются программа, курс, диапазон групп, учебный год и семестр. Watcher обрабатывает **только** период `OFFER_ACADEMIC_YEAR + OFFER_SEMESTER`. Поэтому старые расписания не запускают ingest при включении мониторинга нового семестра.

Для каждого логического слота `program/course/year/semester/group-range` хранится последний SHA-256 в:

```text
watch/kgmu/state.json
```

Если SHA не изменился, повторного ingest и повторного Telegram-сообщения нет. Если файл новый или изменился, он проходит обычный parser/QA pipeline.

Watcher можно запустить вручную:

```text
POST /api/v1/admin/kgmu/watch
X-Admin-Token: <ADMIN_TOKEN>
```

Или включить постоянную серверную проверку:

```text
KGMU_WATCH_ENABLED=true
KGMU_WATCH_INTERVAL_MS=900000
```

Минимальный интервал в коде — 60 секунд; рекомендуемое начальное значение — 15 минут.

## Хранилище и граница публикации

В том же S3/Object Storage используются отдельные зоны:

```text
parser-staging/kgmu/sources/<sha256>/<filename>.xlsx
parser-staging/kgmu/normalized/<sha256>.json
parser-reviews/kgmu/<review-id>.json
watch/kgmu/state.json
schedules/...                                      # опубликованные индивидуальные/legacy keys
schedule-bundles/...                               # атомарные групповые версии
```

Staging и review сами по себе не меняют выдачу действующих подписок.

Для групповой публикации сначала записывается полный immutable bundle, затем обновляется маленький `current.json`. Поэтому подписчик не видит частично обновлённый набор групп.

## Проверка учебного периода

Учебный год и семестр извлекаются из самого XLSX. Параметры ingest сверяются с источником. Например, весенний файл нельзя случайно опубликовать как осенний: такой запрос получает `PERIOD_MISMATCH` и блокируется.

Поддерживаются формы учебного года `2025/26`, `2025-2026`, `2026/27` и эквивалентные записи.

## Admin API

Все маршруты требуют `X-Admin-Token`.

### Загрузить XLSX

```text
POST /api/v1/admin/kgmu/ingest?filename=1_lech.xlsx&program=medicine&course=1&academicYear=2025%2F26&semester=2
Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
X-Admin-Token: <ADMIN_TOKEN>

<binary XLSX body>
```

Для `R`, `C` или `S` с успешным QA по умолчанию ответ получает статус `READY_TO_PUBLISH`. Для `UNKNOWN`, QA-fail, parser error или period mismatch — `REVIEW_REQUIRED`.

### Опубликовать проверенный staging

```text
POST /api/v1/admin/parser-reviews/<review-id>/publish
X-Admin-Token: <ADMIN_TOKEN>
```

Публикация разрешается только для `READY_TO_PUBLISH`, если сохранённый normalized JSON имеет тот же SHA-256 исходника и `QA=PASS`.

### Список review

```text
GET /api/v1/admin/parser-reviews?status=REVIEW_REQUIRED&limit=100
X-Admin-Token: <ADMIN_TOKEN>
```

Можно также запрашивать `status=READY_TO_PUBLISH` или `status=PUBLISHED`.

### Одна карточка

```text
GET /api/v1/admin/parser-reviews/<review-id>
X-Admin-Token: <ADMIN_TOKEN>
```

## Telegram

Переменные контейнера:

```text
TELEGRAM_BOT_TOKEN=<bot token>
TELEGRAM_ADMIN_CHAT_ID=<chat id владельца>
KGMU_XLSX_MAX_BYTES=26214400
KGMU_AUTO_PUBLISH=false
```

Telegram используется в двух случаях:

- `⚠️ REVIEW_REQUIRED` — неизвестный паттерн, ошибка парсера/QA или несовпадение периода; сообщение содержит review ID и явно сообщает, что текущая опубликованная версия сохранена;
- `✅ READY_TO_PUBLISH` — новый XLSX успешно прошёл QA и ждёт ручной публикации.

Если Telegram не настроен или временно недоступен, состояние и review всё равно сохраняются в Object Storage.

## Семестровая и годовая подписка

Семестровая ссылка остаётся привязана к купленному семестру и получает только опубликованное расписание этого периода.

Годовая ссылка объединяет опубликованные `semester-1` и `semester-2` одного учебного года. Если на момент покупки опубликован только первый семестр, ссылка работает с ним; после публикации второго он автоматически появляется в той же ICS-ссылке при обновлении календаря — новый токен и повторный импорт не требуются.

## Production-порядок

1. Merge PR и собрать новый API image.
2. Обновить ревизию Cloud.ru Container Apps этим образом.
3. Оставить `KGMU_AUTO_PUBLISH=false`.
4. Добавить `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`, `KGMU_WATCH_ENABLED=true`, `KGMU_WATCH_INTERVAL_MS=900000`.
5. Проверить вручную `POST /api/v1/admin/kgmu/watch`.
6. Первые реальные обновления публиковать вручную через review ID.
7. Только после накопления безопасной статистики решать, нужен ли `KGMU_AUTO_PUBLISH=true`.
