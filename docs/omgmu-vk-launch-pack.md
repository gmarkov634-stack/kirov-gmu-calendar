## 1. Жёсткое условие публикации

Launch-пост нельзя публиковать, пока одновременно не выполнены:

- официальный источник относится к `2026/2027 + autumn`;
- хотя бы одна продаваемая группа прошла source-bound ChatGPT review;
- полный group batch прошёл canonical input/output QA и ICS preflight;
- группа явно опубликована через canonical publication boundary;
- группа присутствует в live catalog ОмГМУ;
- current-period subscription smoke PASS;
- controlled OmGMU payment/fulfillment E2E PASS;
- landing/device smoke на фактической группе PASS;
- sales gate открыт отдельным осознанным действием.

До выполнения этих условий допустимы только информационные посты о подготовке продукта. Формулировки «календарь доступен», «можно купить», «выберите группу» до gate PASS запрещены.

## 2. Данные, которые подставляются только в день запуска

Перед публикацией получить из live backend, а не из этого файла:

- `{{available_programs}}` — программы, реально присутствующие в current-period catalog;
- `{{available_groups}}` — только фактически опубликованные группы;

Не хранить в launch-тексте статический список групп или цену заранее.

Этот пост допустим только после source-bound review новой версии, QA PASS и explicit publication. Нельзя публиковать его только по факту изменения файла на сайте вуза.

## 7. Запрещённые launch-формулировки

До подтверждения фактического состояния нельзя писать:

- «доступны все группы»;
- «расписание полностью автоматическое»;
- «обновляется мгновенно»;
- «бесплатный месяц» или любую другую trial-длительность без соответствующего product gate;
- заранее зафиксированную цену, если она не сверена с server-owned offer перед публикацией;
- что сервис является официальным сервисом ОмГМУ;
- что данные гарантированно безошибочны.

Корректная позиция: независимый сервис на основе опубликованного расписания; доступность определяется только реально проверенными и опубликованными группами.

## 8. Publication checklist для VK

Непосредственно перед `wall.post`:

1. Проверить OmGMU launch gate и current-period source.
2. Получить live catalog и убедиться, что группы в тексте действительно доступны.
3. Получить live meta и актуальную цену.
4. Проверить фактический sales/trial state.
5. Подставить только подтверждённые значения.
6. Показать пользователю финальный полный текст launch-поста для явного подтверждения.
7. Только после подтверждения выполнить `wall.post` через изолированный OmGMU VK control plane.
8. При наличии изображения использовать текущий безопасный процесс: ручное прикрепление при необходимости и последующая read-only verification.
9. Закрепление поста выполнять вручную, если API capability остаётся недоступной.

Подготовка этого файла **не является разрешением на публикацию**.
