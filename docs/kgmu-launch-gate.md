# KGMU launch gate

## Назначение

Launch gate отделяет две независимые операции:

1. публикацию проверенного расписания;
2. коммерческую доступность checkout.

Расписание должно быть можно обнаружить, разобрать, проверить, опубликовать и обновлять до открытия продаж. Сам факт canonical publication не должен автоматически означать запуск коммерческого интерфейса.

Связанная задача: GitHub issue #81.

## Инварианты

### Gate не влияет на schedule pipeline

При закрытом gate продолжают работать без изменений:

- official source watchers;
- source-bound ChatGPT review;
- canonical input/output QA;
- versioning и diff;
- postprocessing;
- ICS preflight;
- immutable publication storage и `current.json`;
- уже существующие персональные subscription feeds.

### Gate влияет только на новый коммерческий checkout

При закрытом gate новый публичный checkout должен быть fail-closed. Сервер не должен переходить к внешнему платёжному провайдеру.

При открытом gate сохраняются все существующие серверные проверки. В частности, наличие gate не делает группу продаваемой само по себе: для конкретной группы всё равно требуется опубликованное расписание текущего `OFFER_ACADEMIC_YEAR` и `OFFER_SEMESTER`.

### Нет ручных флагов по группам

Доступность группы определяется публикацией её актуального расписания. Gate глобальный и отвечает только за состояние запуска сервиса в целом.

### Frontend не является источником истины

Статическая настройка frontend не должна самостоятельно решать, открыт ли коммерческий режим. UI должен получать безопасный публичный статус от API и при неопределённом/ошибочном состоянии вести себя как при закрытом gate.

## Требуемые состояния

- `closed` — расписания можно публиковать и технически проверять; новый checkout недоступен.
- `open` — checkout разрешён только для опубликованных групп текущего оффера.

Любое неизвестное, отсутствующее или некорректное значение трактуется как `closed`.

## API contract

Публичный API должен предоставлять только безопасное состояние запуска без секретов, например:

```json
{
  "sales": "closed"
}
```

или эквивалентное булево поле. Конкретное имя поля не является частью этого документа; fail-closed семантика является обязательной.

`POST /api/v2/payments` при закрытом gate должен завершаться до любого обращения к платёжному провайдеру и возвращать стабильный код ошибки уровня offer-not-ready.

## Acceptance tests

1. Published current-period schedule + gate closed → расписание читается через storage/technical paths, но новый checkout отклоняется до внешнего запроса.
2. Gate open + published current-period schedule → запрос проходит к существующей payment service.
3. Gate open + schedule absent → `offer_not_found`/эквивалент; внешний запрос не выполняется.
4. Gate value missing/invalid → поведение идентично `closed`.
5. Frontend при closed/unknown состоянии не показывает активный путь оплаты.
6. Existing subscription URL продолжает получать обновления расписания независимо от gate.
7. Production smoke читает публичное состояние gate и не выводит секреты.

## Launch condition

Gate переводится в `open` только после выполнения всех внешних launch prerequisites, записанных в архитектурном документе проекта. До этого production должен оставаться `closed`, даже если первые расписания 2026/27 уже опубликованы.
