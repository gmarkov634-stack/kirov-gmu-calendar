# Versioning расписания v1

## Назначение

Versioning выполняется после успешной входной валидации `schedule-batch` и до постобработки. Его задача — сопоставить новую редакцию расписания с предыдущей, сохранить стабильные идентификаторы занятий и сформировать diff для безопасного обновления подписанных календарей.

Реализация: `api/src/schedule/versioning.js`.

## Идентификаторы

### event_id

`event_id` идентифицирует логическое занятие между редакциями расписания. Если у существующего занятия меняется время, место или другой редактируемый атрибут, сервер по возможности сохраняет прежний `event_id`.

Для нового занятия создаётся новый идентификатор вида `evt_<uuid>`.

### fingerprint события

`system.fingerprint` имеет вид `sha256:<64 hex>` и вычисляется только по семантическому ядру:

- `university`;
- `academic`;
- `audience`;
- `timing`;
- `lesson`.

`source`, `parse`, `derived`, `calendar` и `system` в fingerprint не входят. Поэтому изменение исходной служебной строки или оформления заметок само по себе не считается изменением занятия.

### Ревизия события

Для последующего обновления ICS versioning поддерживает:

- `system.revision`;
- `system.created_at`;
- `system.updated_at`.

Новое занятие получает `revision = 1`. При фактическом semantic change ревизия увеличивается на 1. При неизменённом повторном импорте сохраняются прежние `revision`, `created_at` и `updated_at`.

`created_at` остаётся временем создания логического события, а `updated_at` меняется только при фактическом изменении этого события. ICS преобразует `revision` в `SEQUENCE = revision - 1`.

### content_fingerprint расписания

`schedule.content_fingerprint` вычисляется по метаданным группы/периода и множеству event fingerprints. Порядок событий в массиве на fingerprint расписания не влияет.

Fingerprint используется для идемпотентности и определения одинакового содержимого, но не является идентификатором ревизии.

### schedule_version_id

Новая фактическая редакция получает уникальный `schedule_version_id` вида `ver_<uuid>`.

Если повторно импортировано полностью идентичное содержимое, новая ревизия не создаётся: сохраняется текущий `schedule_version_id`.

Если история выглядит `A → B → A`, второе состояние A получает новый `schedule_version_id`, хотя его `content_fingerprint` совпадает с первым A. Это сохраняет корректную хронологию версий.

`schedule.previous_schedule_version_id` указывает на непосредственную предыдущую фактическую ревизию.

`schedule.version_created_at` фиксирует момент создания конкретной редакции. При идентичном повторном импорте это значение не меняется.

## Порядок сопоставления событий

Сопоставление выполняется консервативно, от наиболее надёжного способа к менее сильному:

1. `event_id`, если он уже присутствует и уникален;
2. уникальный occurrence-anchor: `date + normalized discipline + lesson type + audience`;
3. уникальный source-anchor: `sheet + source references + discipline + type + audience`;
4. одиночная однозначная пара одной семантической категории: `discipline + type + audience`.

Если повторяющиеся события остаются неоднозначными, система не пытается угадывать соответствие. Они остаются `removed + added`, а не искусственно превращаются в `changed`.

## Diff

`versionSchedule(previousBatch, incomingBatch)` возвращает:

- `batch` — новую версионированную редакцию;
- `diff` — результат сравнения.

`diff.counts` содержит:

- `added`;
- `changed`;
- `removed`;
- `unchanged`;
- `total_new`.

Для `changed` дополнительно сохраняются:

- `matched_by` — каким способом было сопоставлено событие;
- `changes[]` — точные пути изменённых полей с `before` и `after`.

Пример изменения времени:

```json
{
  "status": "changed",
  "matched_by": "occurrence_anchor",
  "changes": [
    {
      "path": "/timing/start_time",
      "before": "09:00",
      "after": "10:40"
    }
  ]
}
```

## Правила безопасности

- Изменение времени в ту же дату не создаёт новый `event_id`.
- Изменение даты может сохранить `event_id`, если совпадение однозначно подтверждается source-anchor.
- Повторяющиеся неоднозначные события не fuzzy-match'ятся автоматически.
- `calendar.title`, `calendar.description` и другие производные поля не участвуют в определении semantic change.
- Идентичный повторный импорт является идемпотентным.
- Возврат содержимого `A → B → A` создаёт новую версию расписания и новую ревизию изменённого события, а не откатывает счётчик назад.

## Место в pipeline

Рекомендуемый порядок:

`parse → input validation → versioning/diff → postprocessing → output validation → ICS generation → publish`

Diff должен быть доступен администратору до публикации новой редакции.
